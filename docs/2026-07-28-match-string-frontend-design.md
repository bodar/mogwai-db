# The MATCH-string front end — design

_Swept and measured 2026-07-28 against tinkerpop `origin/master` (submodule `2e56ccc`) and trunk at
L3 1494. Every claim below is a probe result, not an estimate; the method is at the bottom._

This is the design for `docs/outstanding-work.md` **item 7b** — `g.match("MATCH (a:person)-[:knows]->(b:person)")`,
the GQL pattern-STRING form. 25 scenarios (all of `MatchString.feature`), **0 passing**, the single
largest remaining L3 bucket, every one failing `unsupported source step: match`.

## The two premises that were false

7b is filed as **"NEEDS A DECISION, not just implementation"** on two premises. Both are wrong, and
both were cheap to check — the same lesson the hand-rolled-SQL audit recorded four times over: *ask
what the existing thing cannot express, not what it has not yet been handed.*

> **1. "This needs a pattern parser … which collides with locked decision #2 (the parser is
> generated, never hand-edited) unless upstream ships a grammar we can generate from."**
>
> **Upstream ships one.** `gql-gremlin/src/main/antlr4/GQL.g4` — a 311-line combined grammar,
> present on `origin/master`, self-described as *"Minimal GQL grammar covering the MATCH subset for
> node/edge patterns"*. It is a **second language with its own grammar file**, which is exactly why
> it never showed up in `Gremlin.g4`: there, `match` takes an opaque `stringLiteral`
> (`traversalSourceSpawnMethod_match_string`, `traversalMethod_match_string` — both already in our
> generated `parser/`). Nothing needs hand-writing, and locked decision #2 is satisfied by the same
> mechanism it already names.

> **2. "It needs a pattern → IR lowering" (implying new compiler machinery).**
>
> **The compiler needs no change at all.** Hand-desugaring every scenario in `MatchString.feature`
> into Gremlin that trunk compiles *today* reproduces **24 of 25** expected result sets exactly. The
> one miss is not a match() gap — it is an unrelated `concat()` defect (below). There is no new
> StepFn, no new Stream kind, no new provisioning strategy, no new rendering mode.

So 7b is not a decision. It is: **generate a second parser, add one translator module, add one Pass.**

## Shape

Three pieces, each landing on a seam that already exists.

| # | piece | where | what it is | state |
|---|---|---|---|---|
| 1 | `parser/gql/` | generated | `GQL.g4` → antlr-ng → `GQLLexer/GQLParser/GQLVisitor/GQLListener.ts`. Committed, never edited, regenerated by `mise run generate`. | ✅ **LANDED** |
| 2 | `src/gremlin/gql.ts` | front end | parse tree → a neutral pattern graph → `Step[]`. Consumes zero compiler/SQL concepts. | not built |
| 3 | `desugarMatchString` | one `extract` Pass | replaces `match("<gql>")` with `V()…as(seed)` + `match(<patterns>)` [+ a terminal projection]. | not built |

**Piece 1 landed 2026-07-30.** `generate-parser.sh` drives both grammars through one `generate()`
helper, and the Gremlin output is byte-identical afterwards — which is the check that the refactor
shifted nothing. It landed with its own bar rather than as untested dead code:
`test/L1-corpus/gql-parse.test.ts` holds every MATCH pattern in the corpus at **23/23 parsed**
(23 distinct patterns across the 25 scenarios). The patterns are EXTRACTED from `corpus.txt`, so a
new upstream scenario raises the bar automatically; two guards keep the file from going vacuously
green — a floor on the extracted count (a silently non-matching regex would otherwise assert
nothing) and a negative test, since a generated parser that accepted everything would pass the
positive one.

`src/gremlin/gql.ts` sits exactly where `src/gremlin/math.ts` sits, for exactly the same reason:
**`math()` is already a sub-language mini compiler in the front end.** The difference is only that
`math.ts` hand-rolls its lexer/parser (there is no upstream grammar for exp4j formulas) and this one
does not have to. The output side is the same discipline — `math.ts` emits one `Expression`,
`gql.ts` emits `Step[]`, and neither knows anything downstream of that.

### Locked decision #5 holds without an argument

*"The compiler depends ONLY on the IR."* The compiler never learns a GQL concept. What it receives
is the ordinary `match()` IR it already lowers:

```
g.match("MATCH (a:person)-[:knows]->(b:person)").select("a","b").by("name")
                      ⇣  desugarMatchString (extract Pass)
g.V().hasLabel("person").as("a")
 .match(__.as("a").out("knows").hasLabel("person").as("b"))
 .select("a","b").by("name")
```

A GQL grammar bump moves `parser/gql/` and `gql.ts`. Nothing else.

### The seam that makes it free: `stepChain` is already idempotent on a `Step[]`

A nested-traversal argument's payload is *normally* an ANTLR `NestedTraversalContext` — but
`stepChain` (`src/gremlin/frontend.ts:75`) already accepts an already-lowered `Step[]` instead, and
says why: it is *"the single choke point every nested-body consumer resolves through, so making it
idempotent on a `Step[]` lets a synthetic body flow through the WHOLE compiler identically to a
parsed one."* That was built for `TraversalStrategy` rewrites. A GQL pattern is the same object: a
body with no parse tree of its own.

So each pattern is `{ nested: Step[] }` and every consumer below — `parsePattern`, `normalize`,
`lowerElementSteps`, the child seam — is untouched. **This is the "argument-type mismatch, not an
expressiveness wall" tell from `steps/CLAUDE.md`, and here it is already discharged.**

Synthesized steps borrow the `match` step's own `ctx` (as `strategies.ts`'s `synth` borrows a
strategy's), so an error raised deep in lowering still points at the right source span.

### Why the Pass is `extract`, not `fold`

Not a stylistic choice — the category order forces it. `PASS_CATEGORIES` is
`extract < decoration < fold < simplify < verify`, and `ir/pass.ts` states the constraint for
decoration:

> decoration … MUST run before fold: the injectors recurse into raw `{nested}` args … a
> subgraph/partition criterion NOT injected = an unfiltered leak, the fail-closed hole.

A desugar that ran at `fold` would mint its pattern bodies **after** `injectSubgraphRec` /
`injectPartitionRec` had already walked the chain, so a `withStrategies(SubgraphStrategy)` criterion
would never reach them — a silent leak of exactly the kind that comment exists to prevent. Running
at `extract` puts the minted patterns in front of decoration (which then injects into them), in
front of fold (which canonicalizes them like any parsed body), and in `ctx.originalChain` (so
`EdgeLabelVerification` sees the GQL edge labels).

That category's doc comment currently reads *"pull out-of-band flags"*; it should widen to *"…and
surface desugars that must precede decoration"*. Widening the comment is right; adding a sixth
category is not.

## The two structural decisions

Everything else is mechanical translation. These two are the design.

### A. Always pre-bind the seed variable — run `match()` in its ZERO-ROOT regime

`match()` finds its root as *"a start var never used as an end"*. A **cyclic** GQL pattern has no
such var, and the corpus has one (`g_match_cyclicPattern_…`). Measured:

```
g.V().hasLabel('person').match(as('a').out('knows').as('b'),
                               as('b').out('created').as('s'),
                               as('s').in('created').as('a'))
  →  THROW  match() pattern with an unbound start variable ("a") not yet supported

g.V().hasLabel('person').as('a').match(<the same three patterns>)
  →  [{"a":"marko","b":"josh","s":"lop"}]          ✅ the feature's expected row, exactly
```

The fix is not in `match()`. The desugar *already knows* which variable is the BFS seed, so it binds
it in the prefix — and `match()` then takes the path it documents as *"ZERO root variables is a
legitimate shape … when every pattern start was already bound before the `match()`, there is nothing
to seed."* One rule for every pattern shape, cycles included, and no change to root detection.

(That `match()` cannot seed a cycle by itself remains true for hand-written Gremlin. It is a real
`match()` gap, it is now measured, and it is **not** on this critical path — logged below.)

### B. The terminal binding map is a projection, not a new terminal

`match()` deliberately declines to be a terminal: *"it must emit one binding MAP per row and we emit
the traverser."* `g_match_terminalBindingMap` needs exactly that. It falls out of steps that already
exist, dispatched on how many variables the pattern DECLARES:

| declared vars | appended when `match` is the last step | measured |
|---|---|---|
| ≥ 2 | `select(v1, …, vk)` | ✅ `{"a":v[marko],"b":v[vadas]}` — the feature's rows |
| 1 | `project(v).by(__.select(v))` | ✅ `{"p":v[marko]}` (`select(v)` alone yields the VALUE, not a 1-key map) |
| 0 | defer, named | all-anonymous pattern; no corpus case |

Anonymous nodes never appear in the map — they are not declared.

## The translation table

Node/edge constraints attach to the pattern that **first binds** that variable (its BFS discovery
edge); a back-edge re-uses the variable, which `match()` already turns into a constraint rather than
a re-bind.

| GQL | IR fragment | status |
|---|---|---|
| `(a:person)` | `hasLabel('person')` on a's bind site | ✅ |
| `(a {k: v})` | `has('k', v)` | ✅ |
| `(a {k: null})` | `not(__.has('k'))` — GQL `null` means the property is **absent** (`PropertyPredicate.test`: *"passes … if the property is absent and the expected value is null"*) | ✅ `[lop, ripple]` |
| `()` anonymous | a synthetic variable `' anon<N>'` — a leading space, the same collision-proof trick `match.ts` uses for `' traverser'`; GQL `IDENTIFIER` is `[a-zA-Z_][a-zA-Z_0-9]*`, so it cannot be typed | ✅ |
| `-[:l]->` | `as(x).out('l').<constraints>.as(y)` | ✅ |
| `<-[:l]-` | `as(x).in('l').…` | ✅ |
| `-[:l]-` | `as(x).both('l').…` | ✅ (both orientations, as the feature expects) |
| `-[]->` | `as(x).out().…` | ✅ |
| `-[:l {k: v}]->` | `as(x).outE('l').has('k', v).inV().…` | ✅ |
| `-[:l {k: v}]-` | `as(x).bothE('l').has('k', v).otherV().…` | ✅ |
| `-[e:l]->` | **two** patterns: `as(x).outE('l').as('e')` and `as('e').inV().…as(y)` | ✅ — an edge var STARTING a pattern is the shape `match()` gained on 2026-07-27 |
| `<-[e:l]-` | `as(x).inE('l').as('e')` + `as('e').outV().…as(y)` | ✅ |
| `-[e:l]-` | would need `as('e').otherV()` | 🚫 **defers**: `otherV() requires a preceding edge step (no entering-vertex context)`. No corpus case; fails closed. |
| back edge to a bound var | the trailing `as(y)` is a constraint, not a bind | ✅ (the cyclic scenario) |
| `p1, p2` (comma) | more patterns, all in one `match()` | ✅ |
| disconnected components | a GQL-level error, worded as upstream words it | — |
| `$p` | resolved from `match(str, [k: v])`'s map argument (already a JS `Map` by the time `walkArgs` is done); **unbound → throw**, matching the front end's existing `Unbound parameter 'x'`. Upstream instead resolves a missing param to `null`, which then matches *absent* — a fail-open we deliberately do not copy. | ✅ |
| literals `29i` / `1.0` / `'s'` / `true` | the same suffix→subtype tables `frontend.ts` uses, carried as `argTypes` alongside the values | ✅ |

**GQL string escapes are a superset of what `frontend.ts`'s `unquote` handles** — `GQL.g4`'s
`EscapeSeq` includes octal and `\uXXXX`. `gql.ts` gets a complete unescape of its own; widening the
Gremlin-side one is a separate (pre-existing) question and should not ride along.

Direction, orientation and ordering come from ONE BFS over the pattern graph from the seed: it
orients each edge so its start is already bound, orders the patterns, and detects disconnection.
`match()`'s own greedy readiness scheduling then re-orders freely — orientation is the part it
cannot do, which is why the BFS exists.

## What we deliberately do NOT port

Upstream's `gql-gremlin` is a **row-at-a-time DFS executor** with a cost-based planner. Porting it
would be a second implementation of traversal semantics in the exact sense
`steps/CLAUDE.md` forbids, and would break locked decision #3.

| upstream | ours | why |
|---|---|---|
| `DefaultGqlPlanner` — seed selection by `countVerticesByLabel`, edge ordering by label density | seed = the first node in textual order | join order is SQLite's job. A cost model here would be a second planner competing with the one in the engine. |
| `DefaultGqlExecutor` — DFS over `ExtensionStep`s, `PropertyPredicate.test` per element | `match()` → CTE-chained SQL | locked decision #3. |
| Caffeine `QueryGraph` cache | none | one small ANTLR parse per compile; mogwai has no plan cache to hang it on. Revisit with a plan cache, not before. |

`QueryGraph`/`QueryVertex`/`QueryEdge` are still worth reading as the **shape of the parse result** —
that part we mirror.

## Residuals, fail-closed

- **`-[e:l]-`** (undirected *with* an edge variable) — `otherV()` off a re-rooted edge has no
  entering-vertex context. Throws today with that exact message. No corpus case.
- **Zero declared variables at a terminal** (`MATCH ()-[:knows]->()`) — nothing to project.
- **`__.match("<gql>")` in a NESTED position** — the grammar admits it; the desugar would have to
  mint the `V()` re-source inside a child body. Not built; name it.
- **`dedup()` after the bindings** — pre-existing (`dedup() after as() not yet supported`), already
  on the `match()` line of the feature matrix.
- Every deferral names the GQL construct, not the desugared Gremlin. A user who wrote GQL should not
  read an error about `otherV()`.

## Three defects found on the way (all independent of this work)

1. **A `by()` modulator on a `concat()` traversal argument is declined.** Still the *only* thing
   between the design and 25/25. **Re-measured 2026-07-30, and the original diagnosis here was
   wrong** — it was written up as "`concat(<traversal>)` silently drops its arguments", which was
   true when measured and has since been fixed. What remains is one modulator, and the discriminator
   is not `select`, not the label scope, and not the scalar parent:
   ```
   …as('a').out('knows').values('name').concat(__.select('a').by('name'))       ❌ declines
   …as('a').out('knows').values('name').concat(__.select('a').values('name'))   ✅ ["joshmarko","vadasmarko"]
   …as('a').out('knows').values('name').concat(__.select('a').by(T.id))         ❌ declines
   …as('a').out('knows').select('a').by('name')                                 ✅ (same by(), main chain)
   ```
   The middle pair is the clean one: same body, same label, same parent, semantically identical —
   only `by(key)` vs `values(key)` differs. Scenario 25's desugaring with that one substitution
   returns the expected rows exactly (`["marko knows vadas","marko knows josh"]`), so closing this
   is worth exactly the 25th scenario.

   **The mechanism, instrumented 2026-07-30 — and it is NOT a dropped modulator either.** The `by()`
   arrives correctly folded (`body = [{select, modulators: [['name']]}]`) and IS applied. The problem
   is the KIND it produces: `lowerStepsStrict` returns **`result`** — a terminal projection — where
   every child seam needs a stream, so `viaEngine`'s `end.kind === 'scalar'` test rejects it. No
   exception is ever thrown, which is why unswallowing the `catch` printed nothing.

   **And the gap is a FAMILY, not a `concat` quirk.** `select(label).by(key)` composes fine in the
   main chain and is declined in every child position:

   | position | |
   |---|---|
   | main chain — terminal, mid-chain, `.is(…)`, `.count()`, `.concat('!')` | ✅ 5/5 |
   | `concat(__.select('a').by('name'))` | ❌ |
   | `map` / `where` / `order().by` / `group().by` | ❌ 0/4 |

   So the fix is worth far more than the 25th scenario. **Traced to the exact fork, and it is TWO
   halves — a classifier that never admits the step and an emit route that yields the wrong kind.**
   Position in the body is not the discriminator (a modulated select is declined first, mid, or last
   in a child body alike), so the whole shape is simply outside the child vocabulary.

   - **Classify.** `labelSelectOf` (`tail/child-shape.ts`) returns `null` for ANY select carrying
     modulators, so `selectShape` never sees one, `isScalarProducer` never reports scalar, and
     `isSharedScalarChildStep` rejects it. **That guard is LOAD-BEARING — do not simply relax it.**
     It protects `selectOneFromAlias` (`tail/labelselect.ts`), whose element branch ignores
     `step.modulators` completely; letting a modulated select through would silently DROP the `by()`
     and return the element. Verified by reading both branches: the `property` branch does read
     `modulators`, the element branch does not. So the classifier needs a SEPARATE predicate for "a
     single-label select whose `by()` makes it scalar", leaving `labelSelectOf`'s three other
     consumers untouched.
   - **Emit.** `lowerSingleSelect` (`tail/select.ts`) is ALREADY the one correct implementation of
     select-with-`by()` — nested by, key by, `productiveBy`, the `Pop` interactions — which is why
     the main chain works. The child route instead reaches the tail dispatcher and materializes to
     `result`. So the emit half is *reaching `lowerSingleSelect`*, not teaching a second site to
     apply modulators: `selectOneFromAlias` must stay the by()-LESS shape-agnostic resolver, or the
     project acquires exactly the second implementation `steps/CLAUDE.md` forbids.

   Both halves are the audit doc's recurring shape — the seam exists and cannot be *handed* the
   step — so the payoff is all five child positions from one change, not one scenario.

   **✅ Landed 2026-07-30: the fail-closed half.** Enforcing `selectOneFromAlias`'s by()-less
   contract turned out to fix a **live silent wrong answer**, reachable today with no match() in
   sight — `dispatchAlias` routes select() over a VALUE-shaped parent straight to that resolver,
   modulators and all, so `…as('a').values('name').select('a').by('name')` returned `v[marko]`,
   byte-identical to the by()-less form, where `'marko'` is correct. It now defers. No baseline moved
   (no corpus traversal takes that route), and the test pins the DEFERRAL plus both neighbours — the
   by()-less form and the same by() over an ELEMENT parent — so it cannot regress into accepting the
   vertex. **This is also the prerequisite for the classifier half:** relaxing `labelSelectOf`
   without it would have converted a deferral into the wrong answer at five more positions.

   **What is left, and what the first attempt measured.** Relaxing the classifier
   (`labelSelectOf` + folding the by into `selectShape`) was tried and **backed out**, because it
   admits shapes the emitter cannot serve — precisely the classify/emit parity the guardrails
   require ("consumers ASSERT on this classification, so a mismatch is a crash, not a deferral").
   Measured with the relaxation in place:

   | position | with the classifier relaxed |
   |---|---|
   | `where(__.select('a').by('name'))` | ✅ works |
   | `map` / `order().by` / `group().by` | ❌ `child first cardinality requires explicit encounter order` |
   | `concat` (scalar parent) | ❌ still `result`-kinded |
   | `by(T.id)` | ❌ `by(T.id) modulator not yet supported` — emit is narrower than the classifier |

   **The substrate, found 2026-07-30 — and the child-BODY route is the wrong road entirely.** The
   `encounter order` error is a symptom of asking the wrong question: `select(label).by(key)` is not a
   child body at all, it is a **scalar EXPRESSION over the parent row** — project `key` off the
   element named by the label's alias column. No child scope, no cardinality policy, no encounter.
   That is why every fix aimed at the child-body machinery produced a new error one layer down.

   Two candidate homes were checked and rejected before the right one:

   - **`BESPOKE_PROJECTIONS` / `compileScalarChildRows`** — a 5th hard-coded entry in a
     four-projection table the hand-rolled-SQL audit already files as duplication (its item 7).
     Entrenches debt.
   - **The generic `PROJECTORS` table** (audit item 7's own fix) — does not help: every projector
     there builds against the CURRENT element (`c.n`, `c.st.elem`). A select-by projects off a
     *different* element, the one in the alias history, which that table has no notion of.

   The right substrate already exists and **already serves this exact computation**:
   `scalarProp(ctx, key)` with `ctx = aliasCtx(aliasId(col, 'last'), elem)` — the ONE scalar
   projector the audit's item 4 consolidated, parameterized by a `ScalarCtx`. `lowerMathScalar`
   (`tail/mapscalar.ts`) uses precisely that shape today for `math("a + b")`'s `by(key)` modulators
   over as()-label variables. `select(label).by(key)` is the same computation with one variable.

   So the emit half is: recognize the shape in the shared scalar-child entry
   (`tryCompileScalarValueChild`), not in `concat`'s own fallback — one change and all five positions
   get it, versus a per-consumer special case that `steps/CLAUDE.md` forbids. The classifier half then
   admits `kind === 'key'` only, matching what emit serves (`by(T.id)` showed the mismatch: the
   classifier would have admitted a token by that the emitter rejects).

   **A second, separable defect at the same site: the deferral message is wrong.**
   `concat() after a scalar stream not yet supported` names the PARENT shape when the obstacle is the
   ARGUMENT — a scalar parent is fully supported for `concat(' knows ')`, `concat(__.constant(…))`,
   `concat(__.values(…))` and a re-sourced `concat(__.V()…)`. `viaEngine`'s bare `catch { return
   null }` launders every decline reason into `compileFromScalar`'s generic fallback. That
   mis-message is what made this look like a whole-shape gap for two measurement rounds.
2. **`hasNot()` is not implemented** — `step not implemented: hasNot()`. Not a blocker
   (`not(__.has(k))` is the route for `{k: null}` and is verified equal), but it is a one-step gap in
   a common vocabulary.
3. **`match()` cannot seed a cycle** (§A). Sidestepped here by pre-binding, but a hand-written
   `g.V().match(as('a').out().as('b'), as('b').out().as('a'))` still throws.

## Build and test plan

- ✅ **`scripts/generate-parser.sh` gains a second grammar** — DONE. It extracts via
  `git show origin/master:<path>` into a temp file, which **works through the sparse+blobless
  submodule with no change to `init-submodule.sh`'s `SPARSE` set** (verified: `gql-gremlin/` is not
  in the working tree, and `git show` still returns all 311 lines). Output goes to `parser/gql/` via
  `--exact-output-dir -o parser/gql`; byte-stable, committed, reviewed like `parser/`.
- **L1** — the 25 match-string traversals are already in `corpus.txt` and already parse (they are
  ordinary Gremlin with a string argument), so L1's own bar cannot detect this work. ✅ That is why
  `gql-parse.test.ts` now applies the same bar to the SUB-LANGUAGE — 23/23 distinct patterns.
- **New unit test** next to `gql.ts` — GQL string → `Step[]`, over the translation table above. This
  is where orientation, anonymous naming, constraint placement and the terminal projection are
  pinned, because they are decidable from the chain alone.
- **L2** — SQL snapshots for two shapes (a chain and the cycle), so the desugar's SQL is reviewed
  rather than merely executed.
- **L3** — the ratchet is the measurement: **+25, or +24 while the `concat` `by()` gap stands.** No
  other bucket should move; if one does, the desugar reached further than it should have. (Quote the
  delta, not an absolute: the baseline was 1494/2297 when this was written and is 1598/2267 now — the
  denominator moves too, as scenarios leave scope.)
- **The census is the sharper instrument, and it already lists the target.** All 25 traversals sit in
  `test/census/deferrals.tsv` — 23 as `unsupported source step: match`, 2 as
  `match() after a scalar stream` (the `g.inject(1).match(…)` pair, which is what the mid-traversal
  `V()` re-source arm of the desugar is for). Those rows moving from `deferrals.tsv` to `goldens.tsv`
  is a per-traversal signal the L3 count cannot give.
- **L4** — an addendum feature for what upstream does not cover: the undirected-with-edge-var
  deferral, disconnected components, an unbound `$param`, and a single-variable terminal map.

## Risks

- **The seam count is the risk, not the semantics.** The semantics are measured; what is unproven is
  that a *mechanical* translator produces the same strings a human produced by hand. The unit test
  is therefore string-level on `Step[]`, not just end-to-end.
- **`extract`-category placement is load-bearing and invisible.** Nothing fails loudly if someone
  later moves the Pass to `fold` — a SubgraphStrategy criterion just quietly stops reaching pattern
  bodies. Pin it: one test with `withStrategies(SubgraphStrategy)` over a match-string traversal.
- **`GQL.g4` is young.** It is upstream's *"minimal"* grammar and explicitly out-of-scope for
  `WHERE`, `RETURN` and path quantifiers. Tracking it by regeneration is the right posture; building
  anything on top of its current shape is not.

## Method

- `GQL.g4` taken from the submodule at `origin/master`, generated with the project's own
  `bunx antlr-ng -Dlanguage=TypeScript --generate-visitor --generate-listener`. Output: 4 TS files,
  `GQLParser.ts` ≈ 50 KB. **21/21** distinct MATCH strings appearing in `MatchString.feature` parse
  with zero syntax errors.
- Every `MatchString.feature` scenario hand-desugared and **executed** against the seeded modern
  graph through the real `Executor`, results decoded from GraphBinary and compared as unordered bags
  against the feature's expected table. **24/25 equal**; the 25th is the `concat` defect above.
- The residual/deferral rows are direct probes of the named shape, quoted verbatim.
- Scripts were scratch (~200 lines) and are worth re-running after the Pass lands, against the same
  expected tables.
